## Commands

- `npm run dev` — start the dev server (Turbopack, default for Next.js 16)
- `npm run build` — production build (Turbopack by default)
- `npm run start` — run the production build
- `npm run lint` — ESLint (flat config, `eslint-config-next`)
- `npm run test:rls` — REST-level RLS/authorization regression test against the Supabase in `.env.local` (see `docs/SECURITY-REVIEW.md`)

There is no unit-test framework; `test:rls` is the only automated test.

## Architecture

This is a Next.js 16 App Router LMS ("EaseLMS" / Sanggabiz). **Next.js 16 has real breaking changes vs. training data** — see `AGENTS.md`, and read `node_modules/next/dist/docs/` before relying on prior Next.js knowledge. The one that bites most often: **Middleware is renamed to Proxy**. The root convention file must be `proxy.ts` exporting a `proxy()` function — there is no `middleware.ts` at the project root. Async APIs (`cookies()`, `headers()`, `params`, `searchParams`) are async-only, with no sync fallback.

### Reference design

`reference/design_handoff_ease_lms/` contains the design handoff for this product: a high-fidelity, non-production HTML/React prototype (`EaseLMS Dashboard.dc.html` — do not import or run it) plus a `README.md` with the actual design tokens (colors, fonts, spacing) to match when building UI. Treat it as the interactive spec for screens/flows, not as code to reuse. `erd.md` at the repo root is the target data model (entities, relationships, RLS intent) — check it before adding new tables.

The folder layout under `app/`, `lib/`, etc. is intentionally modeled after `enyojoo/easelms/apps/lms` (a reference production implementation of the same product) — `app/admin/*`, `app/learner/*`, `app/api/*` route groups mirror that structure. Some directories are still **empty scaffolding** for features not yet built (payments, email); others — `app/learner/*` and the admin course-authoring flow under `app/admin/courses/*` (see "Admin app shell" below) — are built out. `app/learner/*` includes `app/learner/courses/[id]` (course detail: overview, curriculum, enroll).

The lesson player ("Learn" screen in the reference) lives at **`app/learn/[courseId]/`** — deliberately a top-level route, *not* under `app/learner/`. Every `/learner/*` route inherits `LearnerShell` (nav sidebar + top bar) via `app/learner/layout.tsx`, and Next.js can't remove an ancestor layout for a child route — so the full-screen, no-app-nav player the reference shows has to live outside that tree. Don't move it under `app/learner/` expecting to keep the immersive layout.

**Video and slide lessons carry a `transcript`** (`lessons.transcript`, migration `20261031020000_lesson_transcript.sql`). The accessibility audit found no captions mechanism at all, which stops deaf learners dead on core content (WCAG 1.2.2) — YouTube embeds carry no caption requirement and there was nowhere to put a transcript. It is stored as **plain text, not HTML**, and rendered as text: the content is sentences, and keeping it out of the HTML path means it never needs the sanitiser that lesson content does. The admin field appears for `video` and `ppt` lessons in `LessonsTab`; the learner sees it open below the player (`LessonTranscript` in `LessonPane.tsx`), not hidden behind a tab, since someone who needs it should not have to go looking. It is withheld from non-entitled learners in `getCourseDetail`'s unentitled branch alongside `content` and `video_url` — it is lesson content, not curriculum metadata.

### Learner app shell

`app/learner/layout.tsx` (server) fetches the current user's `profiles` row and passes `name`/`email` into `components/learner/LearnerShell.tsx` (client — owns the sidebar open/closed state). `LearnerShell` renders `components/learner/Sidebar.tsx` (collapsible nav: Dashboard/Courses/Purchase) and a header with `components/learner/UserMenu.tsx` (avatar/name dropdown: Profile/Settings/Log Out, calling the `logout` server action). Future admin/superadmin shells will likely mirror this layout → shell → sidebar/usermenu split rather than duplicating it — check here first before building a new one.

### Admin app shell

`app/admin/layout.tsx` (server) calls `resolveAdminProfile()` (`lib/auth/require-admin.ts`) — redirects to `/auth/admin/login` (unauthenticated) or `/auth/admin/login?error=…` (wrong role) — then renders `components/admin/AdminShell.tsx` (client: collapsible `AdminSidebar` + sticky header with `AdminUserMenu` + a `sonner` `Toaster`), mirroring the learner shell → sidebar/usermenu split noted above. `AdminSidebar.tsx`'s `navItems` array is the single place to add/edit nav entries (Dashboard, Course Management, Learners, Purchase).

**Manage Course** (`app/admin/courses/`) is a fully built list → create → edit flow, not scaffolding:
- `courses/page.tsx` lists courses (`CourseManagementClient` + `CourseListToolbar`/`CourseListCard`, client-side search/status/price filtering) with a **Create Course** button that calls `createDraftCourseAction()` — inserts an "Untitled Course" draft row and redirects straight to `courses/[id]/edit?new=1`.
- `courses/[id]/edit/page.tsx` renders `CourseFormShell` (`components/admin/courses/`), a `react-hook-form` + zod (`schema.ts`) tabbed editor: **Basic Info** / **Lessons** / **Settings** / **Preview**. Lessons (`tabs/LessonsTab.tsx`) are grouped into **modules** (`course_sections` rows, rendered as `SectionCard`s) — admins can add/rename/delete a module and drag lessons to reorder them within or across modules, matching the "Modul 1 / Modul 2" grouping the learner curriculum/sidebar already render. Drag-and-drop uses `@dnd-kit/core` + `@dnd-kit/sortable` (the only DnD library in the repo); `LessonsTab`'s `handleDragEnd` computes the new per-section lesson-id grouping and sends it to `reorderLessonsAction` → `reorderLessons` (`lib/courses-admin.ts`), which updates each lesson's `position` and `section_id` together. `ensureDefaultSection` still exists as the one-time bootstrap that creates a course's first module when a lesson is added to a brand-new course with zero sections. Each lesson can expand into Content, Resources, and a Quiz sub-editor (`tabs/QuizEditor.tsx`). Settings (`tabs/SettingsTab.tsx`) composes level/enrollment fields plus `PrerequisitesSettings.tsx` and `CertificateSettings.tsx`. Preview (`tabs/PreviewTab.tsx`) is **UI-only** — it renders the learner-facing look live from current `react-hook-form` state (no persistence, no new DB read) and coexists with the separate persisted `courses/preview/[id]/page.tsx` route (opened from the list's eye button).
- The reference design (`EaseLMS Dashboard.dc.html`) also specifies a **Course Preview Video** field and **Sequential Progress**/**Minimum Quiz Score** toggles in Basic Settings — deliberately **omitted** from the form because `courses` has no backing columns for any of them; don't add them to the UI without adding the migration first (see the comment atop `components/admin/courses/schema.ts`).
- Admin server actions (`app/admin/courses/actions.ts`, `lessons-actions.ts`, `quiz-actions.ts`, `settings-actions.ts`) follow one shared pattern, distinct from the learner actions style: `"use server"`, call `requireAdmin()` wrapped in try/catch → `{ ok: false, error }` on throw, delegate to a `lib/courses-admin.ts` function, map `{ error }` → `{ ok: false, error }`, then `revalidatePath` and return `{ ok: true, data }` (shared `ActionResult<T>` type). `lib/courses-admin.ts` is server-only (imports `lib/supabase/server`) — never import it from a Client Component, same rule as `lib/courses-server.ts`.
- Design tokens for this whole surface live in `app/globals.css`. **v2 deliberately departs from the reference values for contrast** (WCAG 2.2 AA, see `docs/V2-UPGRADE.md` §2): `--primary: #13707f` (was `#1a7f91`), `--ring: #167384` (was `#35b5c6`, 2.45:1 as text), `--muted-foreground: #566a70`, `--input: #6f939c`, `.bg-brand-gradient` = `linear-gradient(90deg,#167384,#2a6d93)`. Don't reintroduce the reference's lighter teal for text or under white text — primary CTAs (Create Course, Publish/Save, top-level Add Lesson) use `.bg-brand-gradient text-white hover:brightness-105`; nested add-buttons (Add Link/File/Question/Option) are plain `variant="outline"`, matching the reference's own distinction between its one gradient button and everything else.
- **Text lesson content** (`LessonsTab.tsx`'s Content sub-section, `content_type === "text"`) is authored with `components/admin/courses/RichTextEditor.tsx`, a Tiptap (`@tiptap/react` v3 + `starter-kit`/`extension-text-align`/`extension-text-style` (`TextStyle`+`Color` both live here in v3)/`extension-highlight`/`extension-image`) editor with a custom toolbar (heading levels, color, highlight, bold/italic/underline/strike, image upload, blockquote, code block, align, lists) matching `reference/content.png`. It saves HTML into `lessons.content` on blur (same onBlur-autosave convention as the rest of the tab) — **this replaced a plain-text `## heading` convention**, so the learner-side reader (`components/learn/LessonPane.tsx`) now renders `lesson.content` directly via `dangerouslySetInnerHTML` (acceptable since content is admin-authored and Tiptap-constrained; revisit with server-side sanitization if non-admin authoring is ever added) inside a shared `.lesson-prose` class (`app/globals.css`, built on `@tailwindcss/typography`'s `@plugin`) used by both the editor and the reading view so authoring matches output. Image uploads go through `uploadLessonImage` (`lib/storage.ts`) into a **`lesson-content` Supabase Storage bucket** — like the other buckets referenced there, it must be created manually in the Supabase Dashboard (public read), not via migration.
- **`ppt` lesson type** (`lesson_content_type` enum, `supabase/migrations/databaseSetup.sql`) embeds a Google Slides presentation. It deliberately **reuses the existing `lessons.video_url` column** rather than adding a new one — a lesson is exactly one type, so video and ppt never overlap on the same row. `lib/courses.ts` `getGoogleSlidesEmbedUrl()` mirrors `getYouTubeEmbedUrl()`'s shape (parse with `new URL()`, normalize to `/embed`, `null` on anything unparseable) for share/`edit`/`pub` links. The admin picks "Slides Lesson" in `LessonsTab.tsx`'s type list, which shows a "Google Slides Link" input reusing the same `videoUrl` state/save call as the video type. The learner player's `SlidesContent` (`components/learn/LessonPane.tsx`) mirrors `VideoContent` but drops the YouTube-specific `allow` list, keeping only `allowFullScreen`. `LessonContentType` (`lib/courses.ts`) is the single source of truth for the type union — its `Record<LessonContentType, …>` consumers (`LessonsTab.tsx`'s `TYPE_ICON`, `LearnSidebar.tsx`, `CourseCurriculum.tsx`) are exhaustive, so adding a new lesson type forces a compile error at every icon/label map that needs updating.
- **Interactive lessons are built** (`docs/STANDAR-MATERI-INTERAKTIF.md`, migration `20261114010000_lesson_interactive.sql`). A fifth `lesson_content_type`, `interactive`, holding **one HTML file with no JavaScript at all**, rendered **inline** rather than in an iframe — measured 13 Nov: inline, axe sees the material; in a sandboxed iframe it sees nothing, and material that cannot be measured cannot be guaranteed usable. It deliberately does **not** reuse `mixed` (0 rows, but `LessonPane` already treats it as a quiz) and adds **no new column** — the HTML lives in `lessons.content`, which is already the HTML column.
  - Security is three layers. (1) `lib/sanitize-interactive.ts` is a **second sanitiser profile** — never widen `lib/sanitize-content.ts`'s 34-tag list, which also governs text lessons, landing blocks and course descriptions. `input` is checkbox/radio only; `<form>`, `<iframe>`, `<script>` and event handlers are gone. (2) Author CSS is parsed with postcss and every selector is prefixed with `.materi-interaktif`; `position: fixed`/`sticky`, `@import`, `@font-face` and external `url()` are dropped, and `:root`/`html`/`body` are redirected to the wrapper. (3) The wrapper carries `contain: layout style` — not optional: author CSS with no dangerous tag at all was measured covering the whole LMS header including the Log out button.
  - **`lib/courses-admin.ts` picks the profile by `content_type`** at the single save door. Interactive content must never go through `sanitizeRichText` (it would strip `<details>`, `<input>` and every `<style>`, storing the material as dead text); text lessons must never go through the interactive profile. It re-cleans server-side even though the editor already did — what the browser posts is never the guarantee.
  - `components/learn/InteractiveMaterial.tsx` is the wrapper, shared by the player and the admin preview so the two cannot drift. It lives under `components/learn/` on purpose: putting it in the admin editor file would drag the editor and its server action into every learner's bundle.
  - Accessibility is checked **server-side at clean time** (headings, `img` without `alt`, unlabelled checkboxes, tables with no `<th>`), not with axe in the admin browser — axe-core is a 550 KB devDependency, and because the material renders inline the existing `npm run audit:a11y` already sees it. Those checks are warnings, never refusals. Note `sanitize-html`'s types declare an `onOpenTag` hook that **the library never calls**: tsc stays green while the check silently never runs. Use `transformTags["*"]`.
  - `npm run test:interaktif` (`scripts/uji-materi-interaktif.ts`, 36 assertions) throws a hostile file at the sanitiser and checks the *output*, and separately checks that legitimate material survives — `details`, radios, `data-*`, `@media`, `@keyframes`, commas inside `[attr]`, and all three valid labelling patterns. Half the suite exists to catch over-zealous cleaning: a sanitiser that removes everything is safe and useless.
  - **`lib/interactive-guide.ts` is the single source of the team's authoring guide and its worked example**, downloaded as Markdown from `/admin/courses/panduan-interaktif` and linked from the editor hint — the team authoring material has no repository access, so a `docs/…` path was useless to them. It follows `lib/course-markdown/guide.ts`'s pattern: the reader is the author *and* the AI they hand it to, so rules are written as instructions a model can obey. `npm run test:interaktif` asserts the embedded example still cleans with **zero** removals, because a guide teaching a pattern the sanitiser rejects is worse than no guide. **`<form>` is not an allowed tag**, so never hang a selector on a class attached to one — the class disappears with the tag. The demo lesson is in the demo course's Modul 2 (`supabase/seed/01-kursus-demo.sql`).
  - `keTeks()` (`lib/ai/lesson-assistant.ts`) strips `<style>`/`<script>` **with their bodies** — without it the author's CSS is read as lesson text and fed to the chatbot and the translator as hundreds of lines of selectors.

### Supabase integration

Client creation follows the standard `@supabase/ssr` split, in `lib/supabase/`:
- `client.ts` — browser client (`createBrowserClient`), for Client Components.
- `server.ts` — server client (`createServerClient` + `next/headers` cookies), async `createClient()`, for Server Components/Actions. **Never import this (or anything that imports it) from a file a Client Component also imports** — even transitively, this breaks the entire app (not just one route) because `next/headers` can't be bundled client-side. This is why course data is split into `lib/courses.ts` (client-safe types/helpers) and `lib/courses-server.ts` (the actual `createClient()`-based fetch) — follow that split for any future data module needed by both server pages and client components.
- `middleware.ts` — exports `updateSession(request)`, refreshes the session and redirects unauthenticated users to `/auth/login` for any path starting with `/learn` (covers both `/learner/**` and the full-screen `/learn/[courseId]` player — same prefix check, deliberately not two separate conditions). **Wired up** via the root `proxy.ts` (Next.js 16 convention — see above), which calls `updateSession` on every non-static request.

Roles (`learner`/`admin`/`superadmin`) live in a `profiles` table (`supabase/migrations/databaseSetup.sql`), 1:1 with `auth.users`, auto-populated on signup by a trigger. A custom access-token hook mirrors `profiles.role` into the JWT's `app_metadata.role`, so `supabase.auth.getClaims()` gives you the role with no extra query — but the hook only takes effect once enabled in the Supabase Dashboard (Auth → Hooks), creating the SQL function alone isn't enough.

### Auth pages

**Password recovery** is `/auth/lupa-sandi` → email link → `/auth/callback?next=/auth/sandi-baru` → `/auth/sandi-baru`. It deliberately reuses the existing `/auth/callback` rather than taking the recovery link directly: that route is already in Supabase's redirect allow list (Google OAuth uses it), so no dashboard change was needed, and its `safeNextPath()` guard already blocks open redirects. `ForgotPasswordForm` calls `supabase.auth.resetPasswordForEmail` from the browser client, so the flow is PKCE — the code verifier lives in a cookie, which means **opening the emailed link in a different browser than the one that requested it will fail** and land on `/auth/auth-code-error`; that is expected PKCE behaviour, not a bug. `/auth/sandi-baru` redirects to `/auth/lupa-sandi` when there is no session, so the page is never a form that cannot work. Delivery itself rides on whatever Supabase Auth is configured to send with: the built-in sender is rate-limited and intended for testing, so real learner volume needs custom SMTP configured in the dashboard (an account action, not a code change).

`/auth/login` and `/auth/learner/signup` (`app/auth/login/page.tsx`, `app/auth/learner/signup/page.tsx`) are thin server shells around `components/auth/LoginForm.tsx`/`SignupForm.tsx` — client components using `useActionState` against the server actions in `app/auth/login/actions.ts`/`app/auth/learner/actions.ts`, which now return `{ error }` (or, for signup, `{ status: "check-email", email }`) instead of the old `redirect(...?error=...)` pattern. `components/auth/PasswordInput.tsx` wraps `components/ui/input.tsx` with a show/hide toggle and is reused on the change-password fields in `components/learner/SettingsView.tsx`/`components/admin/AdminSettingsView.tsx`. Signup validates with `components/auth/schema.ts`'s `signupSchema` (zod, includes a `confirmPassword` refine check) on both the client (`react-hook-form` + `zodResolver`) and again server-side in the action — never trust the client check alone.

Both forms submit an hCaptcha token via `@hcaptcha/react-hcaptcha`, read from `NEXT_PUBLIC_HCAPTCHA_SITE_KEY` (`.env.local`): signup shows the normal visible checkbox widget; login uses an invisible widget executed on submit, so sign-in stays low-friction. **This only does anything once captcha protection is turned on in the Supabase Dashboard** (Authentication → Attack Protection → hCaptcha, pasting the secret key there) — that's a project-level toggle affecting every `auth.*` call project-wide, so login needed a captcha token too, not just signup, the moment that toggle exists. `.env.local` currently holds hCaptcha's public always-passing test site key (`10000000-ffff-ffff-ffff-000000000001`) as a placeholder for local dev.

Signup's "check your email" branch only fires when `supabase.auth.signUp()` returns no session (i.e. email confirmation is enabled in the Supabase project) — if confirmation is off, `data.session` is present and the action redirects straight to `/learner/dashboard` as before, so the UI is correct either way without needing to know which mode the project is in.

`courses` (`supabase/migrations/databaseSetup.sql`) is real DB data (not mock) — RLS only allows `select` where `status = 'published'`; draft rows are invisible to `anon`/`authenticated`. The landing page reads real course data via `getPublishedCourses()` (`lib/courses-server.ts`) — there is no separate mock data source anymore.

**Per-admin course ownership**: each admin can only create/read/update/delete courses they created — `courses.created_by` (populated by `createDraftCourse` in `lib/courses-admin.ts`) is enforced via RLS, not app-layer filtering, since this project has no service-role client (every admin query already runs as the logged-in admin). The linchpin is `public.owns_course(course_id)`, a `security definer` SQL function (same recursion-avoidance pattern as `is_admin()`) that checks `created_by = auth.uid() or is_superadmin()` — **superadmin is a true superset** and manages every course regardless of owner. Every admin authoring policy that used to be a flat `is_admin()` check (`course_sections`, `lessons`, `resources`, `quizzes`/`questions`/`question_options`, `course_instructors`, `course_prerequisites`, `course_certificate_settings`, and the admin-view policies on `enrollments`/`transactions`/`lesson_progress`/`quiz_attempts`/`quiz_responses`/`certificates`) now derives ownership by joining up to `courses.created_by` via `owns_course()`. Because RLS does the filtering, most admin reads (`getAdminCourseList`, `getCourseDetailForAdmin`, purchases, grading, dashboard stats) needed **no query changes** — they just return fewer rows now; the one exception is `lib/learners-admin.ts`'s `getAdminLearnerList`/`getAdminLearnerStats`, which used to start from the global `profiles` table and had to be rewritten to derive the learner set from (already-scoped) `enrollments` instead. Two things deliberately stay **global** (`is_admin()`, not owner-scoped): the shared `instructors` bio directory (an instructor can be attached to multiple admins' courses) and the storage-bucket write policies (`course-thumbnails`/`lesson-content`/`certificate-assets` — path/metadata-based per-owner scoping was judged disproportionate). `profiles` also stays globally admin-readable (learner names are joined across many unrelated screens). Applied to a live DB via the standalone `supabase/migrations/20260803000000_admin_course_ownership.sql` (uses `create or replace function` / `drop policy if exists` so it's safe to run against existing data — `databaseSetup.sql` itself was updated in place for future from-scratch setups, not left as a separate patch).

**Private (invite-only) courses**: `courses.is_private` (boolean, default false) is **orthogonal to `status`** — a private course can still be draft or published; the meaningful combination is published+private, which means "live, but only for learners an admin explicitly enrolled". It is hidden from the catalog, from `/learner/courses/[id]` (404), and from anon on the landing page. The linchpin is `public.can_read_course(course_id)`, a `security definer` function that replaced the `status = 'published'` test previously inlined in **nine** learner/anon read policies (`lessons`/`resources`/`questions`/`question_options_public` have since moved to the stricter enrollment-gated `can_read_course_content()`, which builds on it — see the curriculum paragraph below) (`courses`, `course_sections`, `lessons`, `resources`, `quizzes`, `questions`, `course_instructors`, `course_certificate_settings`, plus the `question_options_public` view) — visibility now has one definition instead of nine copies, so change it there. Note the `courses` policy must call the function rather than inline the enrollment `EXISTS`: a policy subquery runs with the *caller's* table privileges, and `enrollments` is granted to `authenticated` only, so an inlined version fails with "permission denied for table enrollments" for anon and breaks the entire public landing page. The other load-bearing piece is the `enrollments` self-insert policy, which now also requires `public.is_open_enrollment_course(course_id)` — without it a learner could POST an enrollment row for any course id and thereby grant themselves read access (this also closed a pre-existing hole where learners could self-enroll into *draft* courses). Admin-side enrollment is unaffected, since `"admins insert enrollments"` gates on `owns_course()`. **Learner-side gotcha:** `getPublishedCourses()` (`lib/courses-server.ts`) filters `is_private = false` for the catalog, so any surface that derives a learner's *enrolled* courses by filtering that list will silently drop private courses — this bit `components/learner/CoursesBrowser.tsx`, whose Enrolled/Completed tabs did exactly that. Enrolled-course surfaces must go through `enrollments` instead: use `getEnrolledCourses()` (`lib/courses-server.ts`, full `Course[]`) or `getEnrolledCoursesWithDetails()` (`lib/enrollments-server.ts`), both of which RLS admits because `can_read_course()` passes for a course you're enrolled in. Also note **draft + private is invisible even to invited learners** (`can_read_course()` requires `published`) — the Settings tab warns about this inline, since it reads as the feature being broken. UI: a **Private course** switch in the course editor's Settings → Enrollment Settings (form-bound via `isPrivate` in `components/admin/courses/schema.ts`, saved by the same `updateCourseAction` as the other columns), and a course-centric **Learners** tab (`tabs/LearnersTab.tsx` + `InviteLearnerDialog.tsx`) whose `searchLearners()` (`lib/learners-admin.ts`) deliberately queries `profiles` directly rather than deriving from `enrollments` like `getAdminLearnerList` does — the whole point is finding a learner who has *no* enrollment row yet. Applied to a live DB via `supabase/migrations/20260804000000_private_courses.sql`. **Note:** that same migration work uncovered and fixed a pre-existing bug in `databaseSetup.sql` — `owns_course()` was defined before the `courses` table it reads, and `language sql` function bodies are validated at `CREATE FUNCTION` time, so the from-scratch script could never actually run; the course-dependent helpers (and the `enrollments` table) are now ordered after their dependencies. **Wording:** the word "Free" is deliberately gone from course and purchase UI — `formatCourseAccess()` (`lib/courses.ts`) is the course label (`Privat` → `Publik` → `Rp …`) used by every course card/detail/preview, while `formatPrice()` is money-only and renders `Rp 0` for a zero amount (purchase rows, revenue/spent stat cards). Purchase status badges/filters label `free` as "Publik" and `completed` as "Berbayar"; the stored `TransactionStatus` values, the `enrollmentMode` zod enum, and the admin price filter's `"free"` value are all unchanged — this is a labels-only convention, so don't reintroduce "Free" (or "Gratis") into `formatPrice`.

`course_sections` → `lessons` → `resources` (`supabase/migrations/databaseSetup.sql`) is the curriculum shown on `/learner/courses/[id]` (`lib/courses-server.ts` `getCourseDetail`, rendered by `components/learner/CourseCurriculum.tsx`) and consumed by the lesson player. **Lesson content is enrollment-gated in RLS** (v2 security review, `docs/SECURITY-REVIEW.md`, migration `20261029010000_lesson_content_rls.sql`, `databaseSetup.sql` section 17): `course_sections` and `quizzes` stay readable with the course (`can_read_course()`), but `lessons`, `resources`, `questions` and the `question_options_public` view are readable only through `public.can_read_course_content(course_id)` — `owns_course()` **or** (`can_read_course()` **and** an enrollment for `auth.uid()`) — so anon and non-enrolled users get **no rows** (not nulled columns: RLS can't hide columns). The public "sales page" curriculum comes from the **`lessons_public` view** (`security_invoker = false`, like `question_options_public`; projects only `id, section_id, course_id, title, position, content_type, duration_seconds, resource_count`, filtered by `can_read_course()` so draft/private stay hidden). `getCourseDetail()` builds the lesson list from `lessons_public` and overlays the base-table rows when the caller is entitled; otherwise a lesson has `content`/`video_url` `null`, `resources: []` and `quiz: null` (the curriculum then labels it "Quiz" rather than "N questions"). Any new learner/anon reader of lesson data must follow the same split — embedding `lessons(...)` under `courses`/`course_sections` silently returns an empty list for a non-enrolled user. Admin readers (`lib/courses-admin.ts`) are unaffected (owner policies). Same review also: `profiles` UPDATE is granted only on `full_name`/`notification_email_enabled` (a learner could previously PATCH their own `role` to superadmin); a `guard_quiz_attempt_write` trigger lets learners only open an `in_progress` attempt in an enrolled course (DB-enforced attempt cap mirroring `REGULAR_QUIZ_MAX_ATTEMPTS`) and edit `draft_answers` — `score/passed/status` are written only by `grade_attempt()` (runs as owner) and the owning admin; learners can no longer insert `quiz_responses`; `guard_enrollment_update` makes `enrollments.learner_id/course_id` immutable; Storage buckets have no anon SELECT (no listing; public URLs still work). **C-05 is closed** (`20261031000000_certificate_issuance_lockdown.sql`): every learner write policy was revoked and issuance now runs server-side with the service role after recomputing eligibility in `lib/certificates.ts` — the note that once stood here calling it open was stale. What is still open in `docs/SECURITY-REVIEW.md` is C-12 and C-16, both accepted owner decisions, plus C-14 (`search_path = ''` on `grade_attempt`, deferred to that function's next change).

**Standardized grading + final course grade**: question points are no longer authored per-question — `QUESTION_TYPE_POINTS` (`lib/courses.ts`) is the single source of truth (objective `multiple_choice`/`true_false`/`short_answer` = 1, manually-graded `essay`/`file_upload` = 20). `QuizEditor.tsx` shows a read-only points badge instead of an input, and `saveCourseDraft` (`lib/courses-admin.ts`) derives `questions.points` from `type` on every save — so a question's type change alone repoints the row without any other edit. An assessment's relative weight in the course's **final course grade** is **derived, never authored** — `quizGradeWeight(is_assessment)` (`lib/course-grade.ts`) returns `ASSESSMENT_GRADE_WEIGHT` (3) for a study-case assessment and 1 for a regular quiz, and that constant is the only place to change the ratio. It was briefly a `quizzes.weight` column with a number input in the quiz editor; the column is **dropped** (`supabase/migrations/20260808000000_drop_quiz_weight.sql`) so nothing can look like a stored weight is still honoured — don't reintroduce a per-quiz weight field, the whole point is that the grading model is standardized like `QUESTION_TYPE_POINTS` is. `lib/course-grade.ts`'s `computeCourseGrade()` is the one place the formula lives — `Σ(score × weight) / Σ(100 × weight)`, with an unattempted assessment contributing 0 and a `pending_review` one contributing its provisional objective-only score — and it has exactly three call sites, each scoped differently: `getCourseGradingMatrix` (`lib/grading-server.ts`, admin, one course's whole learner roster, rendered as a trailing "Course Grade" column in `GradingCourseMatrix.tsx` and appended to the course-scope CSV export in `app/admin/grading/export/route.ts`), `getLearnerCourseGrade` (`lib/enrollments-server.ts`, the current learner only, RLS-scoped, shown on `/learner/courses/[id]`), and `checkAndIssueCertificate` (`lib/certificates.ts`, one learner, see below). Don't add a fourth ad-hoc grade computation — reuse `computeCourseGrade`. `courses.passing_grade` (int, default 70) is a third certificate gate alongside the pre-existing all-lessons-complete and all-quizzes-individually-passed checks, evaluated only when the course has at least one quiz; it's authored in the course editor's Settings → Certificate Settings and applies independently of whether the certificate PDF itself is enabled (it also gates the `enrollments.status = 'completed'` flip below). Applied to a live DB via `supabase/migrations/20260806030000_standardized_grading.sql`, which also backfills existing `questions.points` to the standardized scale — that backfill changes the denominator for already-`graded` attempts on mixed quizzes going forward without recomputing historical `quiz_attempts.score`, so past scores may no longer match what re-grading today would produce.

**Grading screens show every submitted attempt, not just what needs a human** (`supabase/migrations/20260807000000_grading_all_attempts.sql`). This — and `grade_attempt()`'s `pending_review` branch generally — predates the normal-quiz/study-case split above and now exists mainly as a **backstop for legacy mixed quizzes and the reserved `matching`/`fill_in_blank` enum values**: `grade_attempt()` still grades essay/file_upload/keyless-short_answer by exclusion (`else v_ok := null`), it just can no longer happen for newly-authored content because `validateQuizzes()` won't let a normal quiz contain one. Don't remove this machinery — old courses saved before the split are still live and gradeable through it. Three things used to conspire to make auto-graded scores invisible, and all three are load-bearing if you touch this area: (1) `public.admin_pending_attempts` — the flat view behind all three `admin_grading_*` RPCs — was gated on `qa.status = 'pending_review'`, so `/admin/grading` never listed a course whose quizzes are all objective, and the matrix at `/admin/grading/course/[courseId]` is only reachable *through* that list; it now covers `status <> 'in_progress'` and exposes `status`, with `admin_grading_stats()` keeping `attempt_count` pending-only via a `filter (where …)` so the "Attempts Pending Review" card still means what it says. (2) `grade_attempt()`'s `pending_review` branch discarded the objective sub-score it had already computed, leaving `quiz_attempts.score` null; it now persists that score while leaving `passed` null, so `checkAndIssueCertificate`'s `passed = true` gate still withholds the certificate and `finalizeAttempt` (`lib/grading-admin.ts`) overwrites the provisional value on manual grading. (3) `CellView` (`GradingCourseMatrix.tsx`) rendered the score and the per-question grade inputs as an exclusive either/or, so a mixed quiz showed only the inputs — the score now always renders, italic + "pending" while provisional, and a cell with no `cell.grades` (i.e. `isManuallyGraded` matched nothing) is read-only, which is the entire auto-graded case. The CSV export (`app/admin/grading/export/route.ts`) gained a `Quiz Score` column and no longer 400s on a course with no manually-graded questions; the import path is untouched because it keys off `Q N Score (<question_id>)` headers and ignores everything else.

**A quiz is either a normal quiz or a study case, never a mix — chosen once, at creation.** `file_upload` is still an answer *format* of Essay, not a type: picking Essay reveals an **Answer format** radio (`ANSWER_FORMATS` in `QuizEditor.tsx`) whose two values write `type: "essay"` (rich-text answer) or `type: "file_upload"` (link input) to the same question row. Both DB enum values stay — Postgres can't drop one, they already score identically, and `QuizPlayer.tsx`/`EssayAssessmentPlayer.tsx`/`SubmissionPreviewDialog.tsx`/`QuizPreview.tsx` branch on `file_upload` to render a link instead of sanitized HTML (the stored `response` payload shape genuinely differs). But essay/file_upload is **only reachable via "Add Study Case"** on an empty quiz — `QUESTION_TYPES` (the "Add Question" picker) offers only `multiple_choice`/`true_false`/`short_answer`, so a normal quiz can no longer contain one. `CourseDraftContext`'s `addQuestion` action takes an `isAssessment` flag used only when it lazily creates the `DraftQuiz` row, and `deleteQuestion` sets `lesson.quiz = null` once a quiz's last question is removed — that's how an author "changes the mode": delete down to empty, then pick again. `QuizSettings` shows the mode as a read-only badge (no toggle) once a quiz has any question.

**Quizzes can't be saved half-authored, or mixed.** `validateQuizzes()` (`lib/course-draft.ts`) rejects an empty prompt, a `multiple_choice` with fewer than two options / a blank option / no correct option, a `true_false` with no correct option, and — since normal-vs-study-case became a hard split — a `short_answer` with no accepted answers, an essay/file_upload question outside a study case, and a study case with more than one question or a non-essay first question. These mirror what `grade_attempt()` actually does with a malformed row (marks it wrong for every learner while still counting its points in the denominator) and, for the split itself, guarantee a normal quiz is always fully auto-graded and a study case is always exactly one manually-graded question — no per-quiz mix of `graded` and `pending_review` semantics for newly-authored content. (Existing courses saved before this rule may still have a mixed quiz; `validateQuizzes` blocks Save the next time that course is edited, but nothing retroactively migrates the row — see the grading-legacy note below.) It is a standalone pass rather than a zod `.superRefine` because `CourseFormShell.onSubmit` flattens zod issues to `issue.path[0]`, which would collapse a `sections[i].lessons[j].quiz.questions[k]` path to the key `"sections"` and render nowhere. It blocks Save to Draft as well as Publish (localStorage autosave means nothing is lost), switches to the Lessons tab, and routes messages through `QuizIssuesContext.tsx` so `LessonCard` can badge a collapsed lesson and `QuestionCard` can highlight the question — both **adjusting state during render**, not in a `useEffect`, since the React Compiler lint rejects setState-in-effect. `saveCourseDraft` runs the same function server-side as a backstop.

`enrollments` (`supabase/migrations/databaseSetup.sql`) links a `profiles.id` learner to a `courses.id`, unique per pair, `status` `active`/`completed`. Unlike `courses`, RLS here is **authenticated-only and own-row** (`auth.uid() = learner_id`) — never anon-readable, since enrollment data is private. Enrolling happens via the `enroll` server action (`app/learner/courses/actions.ts`), which `upsert`s with `ignoreDuplicates` so re-clicking Enroll is a no-op rather than an error, then `revalidatePath`s the Courses list, the course detail page, and the Dashboard. `enrollments.status` **is** flipped to `completed` (with `completed_at`) once a learner finishes every lesson and passes every quiz-type lesson — `checkAndIssueCertificate` (`lib/certificates.ts`) does the rollup and there's now an enrollment UPDATE policy (own-row + admin) to allow it. Admins can insert/delete/update a learner's enrollment (Learner Management screen) only when they own the enrollment's course (`owns_course(course_id)` — see the per-admin ownership note above; superadmin unaffected); learners themselves still have no unenroll path.

`lesson_progress` (`supabase/migrations/databaseSetup.sql`) tracks per-lesson completion, keyed by `enrollment_id` (not `learner_id` directly — it has no learner column, so every RLS policy checks ownership via an `EXISTS` join through `enrollments`). Has select **and** update policies (unlike `enrollments`, which only allows insert) because `toggleLessonComplete` (`app/learn/[courseId]/actions.ts`) `upsert`s on `(enrollment_id, lesson_id)` — the reference's interaction is a **checkbox in the lesson sidebar** (toggle on/off), not a one-way "mark complete" button, so re-toggling needs to actually update the row both ways, not silently ignore the conflict.

Video lessons store a plain YouTube URL in `lessons.video_url` (any of `youtu.be/<id>`, `watch?v=<id>`, `/embed/<id>`); `lib/courses.ts` `getYouTubeEmbedUrl()` normalizes it to an `/embed/` URL for the player's `<iframe>`. Returns `null` for unparseable URLs — `components/learn/LessonPane.tsx` falls back to a "No video available" message rather than rendering a broken iframe.

**When building any screen from the reference, check the exact HTML/JS in `EaseLMS Dashboard.dc.html`, not just a screenshot or the README summary.** The Learn player was first built from a general impression of the layout and missed several concrete, checkable details the source actually specifies (the sidebar's Course-content/AI-Assistant tabs, per-module `{done}/{total}` counts, checkbox-per-lesson with a type+duration subline, and the Overview/Notes/Q&A tab bar below the lesson content) — all easily confirmed by grepping the relevant `data-screen-label` block and its state bindings (`sideTab`, `learnTab`, `learnDone`, etc.) before writing the component. **v2 removed the player's inert "Notes" and "AI Assistant" tabs** (and the Q&A placeholder): they looked usable but saved or answered nothing, which the digital learning standard treats as a defect (every control leads to a real view). Only add them back with a real backend (e.g. a `lesson_notes` table). The `courses.language` column (defaults to `'Bahasa Indonesia'`) is rendered in both the course detail page and the admin preview's Overview tab.

Both clients read `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (anon key) from `.env.local`. No service-role key is configured yet — anything requiring elevated DB access (bypassing RLS) needs one added server-side only, never exposed via `NEXT_PUBLIC_*`.

`supabase/migrations/databaseSetup.sql` is the single consolidated schema setup script — run manually in the Supabase Dashboard SQL Editor (there is no local Supabase CLI project linked yet, `supabase init`/`link` has not been run). It replaced an earlier one-file-per-schema-addition layout now that the schema has stabilized; there is no seed file — courses are authored through the admin course-builder (`app/admin/courses/*`), not mock/sample SQL.

**Not yet built (per `erd.md`, whose status markers were reconciled to reality):** one ERD entity remains unbuilt — `brand_settings` (site name / logo / primary color) has no table or admin screen (it's only partially superseded by `landing_content`, the superadmin-authored landing page at `/admin/landing`).

**Landing block types** (`lib/landing-blocks.ts`): `hero`, `stats`, `categories`, `courses`, `features`, `steps`, `instructors`, `alumni`, `logos`, `gallery`, `testimonials`, `faq`, `cta` — the set a competitor scan of Hacktiv8, Digital Skola, MySkill and RevoU found on essentially every Indonesian LMS landing page. `categories` and `courses` always render **live data** (real categories + published-course counts, each card linking to a pre-filtered `/kelas`). `stats` (platform totals **minus demo `@contoh.test` accounts**), `instructors` (the `instructors` table via `listPublicInstructors()`) and `testimonials` (`course_feedback`) default to live data but carry a **`source: "real" | "manual"` switch** (`SourceToggle` in `BlockEditor.tsx`) with a `manual` list — an owner decision of 2026-11-05 (`docs/STANDAR-HALAMAN-DEPAN.md` §2) that replaced the earlier "numbers cannot be typed in" rule; the editor shows the staleness warning whenever manual is selected, because a number that is never updated reads as a made-up one. Image-heavy blocks (`logos`, `gallery`) take **bulk uploads** (`BulkImageDropzone`: many files at once, one item per file, name from the file name). Landing images go to the dedicated **`landing-assets`** bucket (`uploadLandingImage`, migration `20261105010000`; public read, `is_admin()` write; no SVG). Don't style a hidden block with `opacity-*`: dimming a container dims its text too, which dropped the "Hidden" badge below 4.5:1 (axe color-contrast, serious) — use a dashed border and a tinted background instead.

**`/admin/landing` and `/admin/seo` share one builder shell.** `components/admin/builder/BuilderShell.tsx` is the sticky toolbar (status pill, undo/redo, discard, restore defaults, open-in-new-tab, Save draft, Publish), the preview slot, and the tab strip; both screens pass their own preview and tabs into it. One column, not two — the preview is full width, because a side panel shrinks the preview on exactly the screens people work on. **Save is split from Publish**: `blocks_draft` / `blocks_en_draft` / `theme_draft` on `landing_content` and `seo_draft` on `site_seo` hold unpublished work. The public page reads only the published columns and knows nothing about drafts — `getSeo()` never selects `seo_draft`, which is what keeps an unpublished draft out of search results, since RLS locks rows and not columns. **Click any section in the preview to edit it**: the whole section is one overlay button (safe because the rendered content is `pointer-events-none`), which also switches the tab strip to Section settings. Blocks listed in `FLOATING_BLOCKS` render nothing in flow — the WhatsApp button is `fixed` — so the canvas draws them as a named card instead; a zero-height overlay button fails the 24x24 target size (WCAG 2.5.8). Undo/redo lives in `hooks/use-riwayat.ts` and **merges consecutive edits to the same field within 700ms**, so one undo reverses one thing a person did, not one keystroke. The toolbar's full-bleed `-mx-*` must match `<main>`'s padding in `AdminShell` exactly (`p-4 sm:p-6 lg:p-8`); over-reaching by 4px overflowed 320px and failed WCAG 1.4.10, invisibly on wide screens.

**Social proof names invented parties only.** Blocks that make factual claims about third parties — `alumni` (names, roles, employers), `logos` (partner names) — ship filled with clearly invented organisations ("Universitas Contoh Nusantara", "CV Mitra Nusantara", "Toko Daring Sekar"), never a real company. The landing page is live in production, so an alumni quote crediting a real employer is a false endorsement on a public site, not a placeholder. The editor hints for both blocks say so, and the owner replaces them with real stories once the people involved have agreed. `stats`, `instructors`, and `testimonials` are never seeded at all: they read live rows (`public_platform_totals`, `instructors`, `course_feedback`) and inventing those numbers would be a false claim about the business itself. Each of those three renders nothing when its data is empty, so showing them early costs nothing.

**An instructor's `title` and `bio` are content, not interface.** `scripts/i18n-check.mjs` pulls them into `ISI` alongside course titles and lesson names: one person writes them once about themselves, so they stay in whichever language they were written, in both locales. Translating them would mean a second authoring surface for every instructor.

**The landing page borrows RevoU's rhythm, not its look.** `docs/STANDAR-HALAMAN-DEPAN.md` records what was measured and what was taken: proof before promises (a logo wall sits above the programme list), numbers on the logos rather than adjectives, alumni shown as before → after, community photographed rather than described, and no two adjacent sections sharing the same "centred heading + bordered card grid" shape. Colours and type stay ours — the teal tokens in `app/globals.css`, untouched. The scrolling logo wall (`components/landing/LogoMarquee.tsx`) duplicates its list and shifts -50% rather than measuring width in JavaScript, pauses on hover and focus (WCAG 2.2.2), and under `prefers-reduced-motion` stops at the start and turns the row into a scrollable one — the global reduce rule would otherwise snap it to its end state and hide half the logos. `FloatingWhatsApp` is a block like any other so hiding and ordering work on it; its green is `#075e54`, the darkest official one, because white 14px text needs 4.5:1 and the brighter greens give 4.1:1 and 1.8:1.

**The landing page is bilingual and block-shaped.** `landing_content.blocks` (jsonb, ordered list — see `lib/landing-blocks.ts`) is what `/` actually renders; `blocks_en` holds the English version and is **nullable on purpose**: `getLandingBlocks(locale)` falls back to the Indonesian blocks when it is null, so the page is never empty just because a translation has not been written. `/admin/landing` edits one language at a time behind a language tab, and its preview iframe passes `?bahasa=` so the superadmin sees the version being edited without changing their own interface language (`app/page.tsx` nests a second `LocaleProvider` for that, so client components inside follow the override too). **Do not write to the flat `heading` / `features` / `featured_course_ids` columns**: they are only the fallback that seeds `defaultBlocks()` when `blocks` is null, so editing them changes nothing a visitor sees — an admin form that did exactly that was deleted on 2026-11-04 (and its one live control, the featured-courses picker, moved into the Courses block where `courseIds` is genuinely rendered). Saves use `update … eq("id", true)`, never `upsert`: upsert's INSERT path checks the other columns' NOT NULL constraints before conflict resolution, so an upsert touching only `blocks` always fails. Everything else in the ERD is implemented. Commerce is built as free-only scaffolding (`transactions` table + `/admin/purchases` + `/learner/purchase`); only the real payment-**gateway** charge flow is deferred.

### Public catalogue (`/kelas`)

`/kelas` and `/kelas/[id]` are the **unauthenticated course catalogue and course preview** — a visitor browses classes, reads the full curriculum outline, and only meets the sign-in wall when they press Enrol. They sit outside `proxy.ts`'s `/learn` prefix guard, so nothing redirects them.

- `lib/catalog-server.ts` is the only reader. It uses the **anon client** for course rows (RLS's `can_read_course()` already permits published, non-private courses) and the service-role client for exactly two non-personal extras: the per-course rating summary (`course_feedback` is authenticated-only) and the certificate-enabled flag (`course_certificate_settings` is owner-only). Both are projected down to numbers/booleans — never names, comments, or ids.
- **`AMBANG_ANONIMITAS = 5`** gates both the learner count and the rating: below five data points they render as nothing, matching the rule `/api/public/stats` already applies ("1 learner on this course" names a specific person). Don't lower it to make a demo look busier.
- Filtering/sorting happens **in memory** on purpose — the catalogue is tens of rows and two of the filters (level, duration bucket) need normalisation that no single `eq` expresses. The comment in `getCatalogCourses` says when to move it into the query.
- Filter state lives entirely in the URL (`?cari=&tingkat=&akses=&durasi=&urut=`) via `useListParams`, so a filtered catalogue is shareable and server-rendered.
- The curriculum preview renders from `getCourseDetail()`'s `lessons_public` path: lesson **titles, types and durations** are deliberately public, lesson **content** never is (RLS withholds it, not the component).
- Enrol has four states in `EnrollPanel` — anonymous (links to `/auth/login?next=…`), signed-in-and-free (calls `enroll`, then pushes to `/learn/<id>`), paid (no payment gateway exists, so it says so instead of offering a button that `enroll` would reject), and already-enrolled. **Check `isSignedIn()` before offering the enrol button**: `getEnrollmentProgress` returns `enrolled: false` for anonymous visitors too, so keying off it alone shows anonymous people a button that always fails.
- `?next=` is honoured by `app/auth/login/actions.ts` and validated with `safeNextPath()` — never redirect to a raw query parameter.

**Course categories** (`categories` + `courses.category_id`, migration `20261105010000_course_categories.sql`) are a **shared directory, modelled on `instructors`**: anyone can read them (the public catalogue needs to), any admin can create them, and `courses.category_id` is `on delete set null` so removing a category never deletes a course. They are created **inline from the course editor** (`CategoryPicker`, mirroring `InstructorPicker`) rather than from their own admin screen — the admin menu is already at 11 entries (standards item A4), and people need a category exactly while authoring. The catalogue filters on `slug`, not id, so a shared `/kelas?kategori=pemrograman` link stays readable and survives a rename; only categories that actually have published courses are offered as filter options, because an option that guarantees zero results is a dead end you only discover after clicking.

**`courses.level` has one stored vocabulary**: `beginner` | `intermediate` | `advanced`, or NULL. It used to have two — the editor's picker wrote English keys while the `.md` importer wrote whatever the author typed, and the guide tells them to write "Pemula"/"Menengah"/"Lanjutan". That split was invisible until the catalogue needed to *filter* by level, at which point one concept sat in two buckets that never met. `lib/course-level.ts` owns the canonical list, `normalizeLevel()` (which still accepts the old Indonesian spellings) and `levelLabel()`; migration `20261104020000_normalize_course_level.sql` rewrote the stored rows. Display labels come from the dictionary, so level is bilingual — don't store a display string.

**English plurals:** `lib/i18n/plural.ts` picks between a `…One` and a plain key. Indonesian needs no such thing, which is why counters written before the bilingual work read "1 practice quizzes" in English. Any new public-facing counter needs both keys.

### Public API

`GET /api/public/stats` (`app/api/public/stats/route.ts`) is the one **unauthenticated, cross-origin** endpoint in the app, meant to be consumed by other websites. It returns aggregate numbers only — course titles plus per-course learner counts and platform totals. **No names, emails, or person ids, ever.** That boundary is enforced in the database, not in the route: the two views it reads (`public_course_stats`, `public_platform_totals`, migration `20261030000000_public_stats_views.sql`, `databaseSetup.sql` section 18) are `security_invoker = false` so they can count rows in `enrollments`/`profiles`, which are closed to anon — so **never add an identity column to those views**, and never widen the route to return one. Because the exposure lives in the views, the route uses the plain anon key: no service-role key touches a public path. Draft and private courses are excluded, matching the learner catalogue. Responses are cached (`s-maxage=60`) and carry `Access-Control-Allow-Origin: *`, which is only safe *because* there is no personal data in them. Two guards exist because a plain count is not automatically anonymous: per-course `learner_count` is **null below 5** (on a small platform "1 learner on this course" names a specific person — the very who-takes-what fact that was refused), and demo content is flagged per row via `is_demo` (`slug like 'kursus-demo-%'`) plus `demo_learner_count`/`demo_course_count`, which drive a self-disclosing `notice`. A deliberately-labelled "Kursus Demo - Uji Coba API" row exists in production purely so the endpoint has something to return; deleting it is safe. Note the views carry **explicit `revoke all` before the grants**: Supabase's default privileges hand every new view INSERT/UPDATE/DELETE for anon, and a view has no RLS — the grant *is* the only control, so a later refactor that made these views auto-updatable would otherwise have turned them into anon write paths running with the view owner's rights. Finally, the anon key is public, so `/rest/v1/public_course_stats` can be read directly: the route is presentation, never a filter.

### Integration API (`/api/v1`) and webhooks

The authenticated, machine-facing API for a customer's IT team — distinct from `/api/public/stats`, which is anonymous and aggregate-only. Five routes under `app/api/v1/`: `GET courses`, `GET learners`, `GET enrollments`, `POST enrollments`, `GET certificates`. `lib/api-v1.ts` owns the shared shape — `jagaApi()` (auth + scope), `halaman()` (`?limit=` max 200 / `?offset=`), `jawab()` (`{data, pagination}`), `galat()`. **Field names stay English** even though the admin screens are Indonesian: this is a machine contract, and the in-app guide at `/admin/integrations/petunjuk` is the Indonesian-language part.

It deliberately does **not** reuse Supabase's own REST endpoint: the anon key is public and cannot be revoked in parts, and revocable, scoped, observable credentials are the whole request. Keys are `sgb_<8 hex>_<48 hex>`; only the SHA-256 of the whole key is stored (`integration_api_keys.key_hash`, compared with `timingSafeEqual` so verification time leaks nothing), while the prefix is stored in clear so a key leaked into a log can be identified and revoked. `lib/api-keys.ts` is the client-safe half, `lib/api-keys-server.ts` the reader/writer. Scopes are `read` and `write`; **`POST /api/v1/enrollments` is the only write path in the entire API**, and it never creates accounts — an unknown learner is `404 learner_not_found`, because one mistyped email should not conjure a person with an unclaimable learning history.

**Webhook events are queued by database triggers, not by application code** (`20261112010000_webhook_antrean.sql`): `enrollment.created`, `course.completed`, `certificate.issued`. Three separate paths create enrollments, so a trigger is the only way to cover all of them with no fourth path that forgets. Every trigger body is wrapped in `exception when others then null` — **a webhook must never abort an enrollment or a certificate**.

Delivery does **not** depend on the scheduler. The Vercel account is on the **Hobby plan, which rejects any cron more frequent than daily** (a deploy failed with exactly that error), and a webhook that arrives tomorrow is not a webhook. So `kirimAntrean()` lives in `lib/webhook-kirim.ts` and is called through `after()` from `next/server` right after an event is queued (`app/api/v1/enrollments/route.ts`, `lib/certificates.ts` — the latter wrapped in its own try, since `after()` is only valid inside a request and `checkAndIssueCertificate` is also called from scripts). `app/api/webhooks/kirim/route.ts` is now only a daily 03:00 safety net guarded by `CRON_SECRET`. The queue remains the guarantee: a failure means delayed, not lost. Don't "fix" the cron back to `* * * * *` — the plan rejects it at build time. Retry backoff is `JEDA_COBA_ULANG_MENIT` in `lib/api-keys.ts`, and the time comparison is done by Postgres (`webhook_antrean_siap()`, migration `20261112020000`) rather than Node — comparing `next_attempt_at` against the Node clock made the first flush always miss its rows.

**Endpoint URLs are validated where they are SAVED, not where they are sent** (`app/admin/integrations/actions.ts`): https only, and no in-network address (localhost, RFC1918, link-local, `.internal`). The sender runs on our servers, so a stored URL is an SSRF hole, and one bad row that got in would be retried by the scheduler again and again.

### Course recommendations

Two different questions, two different cards, both on `/learner/dashboard`: `JobCoursesCard` answers "what is required for my position" (job title, `lib/org.ts`), `RekomendasiCard` answers "what makes sense to study next, given what I have finished" (`lib/rekomendasi.ts` + `lib/rekomendasi-server.ts`). They complement each other — don't replace one with the other.

`hitungRekomendasi()` is a pure function so the thing that decides what a learner sees can be tested without a database. Three signals with whole-number weights (same category 3, next level up 2, popular 1), at most three cards, already-enrolled courses never offered. **Every card carries its reason** — `docs/STANDAR-DIGITAL-LEARNING.md` names a recommendation without a reason as an anti-pattern — and the reason is assembled on the server, since a reason assembled in two places soon reads differently in each. A cleverer model cannot explain itself, and a recommendation that cannot be explained cannot be corrected when it misses. Note `public_course_stats` keys its course column `id`, not `course_id`.

### Department report (F3)

`/admin/tracking` carries a superadmin-only **Laporan per departemen** section (`components/admin/tracking/LaporanDepartemen.tsx`), sitting next to `BehaviorSummary` behind the same gate. It is a section rather than its own route on purpose: the admin menu is already at eleven entries (`docs/STANDAR-PLATFORM-DIGITAL-LEARNING.md` A4 warns about growth), and that page is already where cross-cutting aggregates live. The aggregate deliberately does **not** live in `lib/insight-server.ts` — everything there is scoped to one course, while this is organisation-wide.

Three rules from `docs/MVP-AI-KORPORAT-STATUS.md` govern it, and two are enforced by **types**, not by good intentions:

- **Groups under five people show no figures** (`AMBANG_LAPORAN` in `lib/laporan-departemen.ts`, same value and reasoning as `AMBANG_ANONIMITAS` in `lib/catalog-server.ts`). The *figures* are withheld, not the row — dropping the department makes the totals never add up and reads as broken data, while a row that says why it is empty tells the admin what is missing. Headcount is always shown: it is org-structure fact already visible on the Jabatan & Departemen screen, not behaviour.
- **The AI summary only ever sees aggregates.** `keAngkaRingkas()` produces `AngkaRingkas`, a type with no field for an id, a person's name, an email, or a course title. `lib/ai/report-summary.ts` takes nothing else.
- **People are never ranked.** No function in that module returns a per-person row. Departments may be compared; people may not.

Summaries are stored in `ai_report_summaries`, **one row per language** (`scope` = `departemen:id` / `departemen:en` via `lingkupRingkasan()`). With a single row for all languages, an English reader got an English interface wrapped around an Indonesian summary, because the last writer won. The figures used are stored alongside in `figures`, and staleness is decided by comparing them with `samaAngka()` — **not** `JSON.stringify`, because `jsonb` reorders object keys, which made every freshly written summary immediately label itself out of date.

Token cost is capped per superadmin per day (`BATAS_TOKEN_LAPORAN_HARIAN`); one summary measured ~768 tokens. The action re-reads the figures server-side rather than trusting numbers posted from the browser — otherwise anyone who can call it could have the model summarise invented figures and store the result as if it were a real report.

### Notifications

`notifications` (`supabase/migrations/databaseSetup.sql` §12, applied to a live DB via `20260805000000_notifications.sql`) backs the bell in the learner header. Rows are **only ever created by a database trigger** — there is deliberately no insert policy and no insert grant, mirroring how `profiles` rows come only from `handle_new_user()`; learners get own-row select + update (update exists solely so the bell can set `read_at`). `notify_on_enrollment()` fires `after insert on enrollments` and is `security definer` because it writes a row belonging to a *different* user than the caller (an admin acting for a learner). It is a trigger rather than app code because three separate paths create enrollments — `toggleLearnerEnrollmentAction` (learner-centric `EnrollModal`), `enrollLearnerAction` (course-centric Learners tab), and the learner's own `enroll` action — and a trigger covers all of them with no way to add a fourth and forget. Two deliberate silences: it skips self-enrollment (`auth.uid() is distinct from new.learner_id`), and being `after insert` only it produces no duplicate when `enrollLearnerInCourse`'s upsert resolves to an UPDATE. `lib/notifications-server.ts` `getNotifications()` feeds `components/learner/NotificationBell.tsx` through `app/learner/layout.tsx` → `LearnerShell`, so the bell is present on every `/learner/*` page.

**Email is not wired up.** `profiles.notification_email_enabled` and its Settings toggles (`components/learner/SettingsView.tsx`, `AdminSettingsView.tsx`) predate any delivery mechanism — there is no email provider, no library, and `app/api/` is an empty `.gitkeep`, so that toggle is currently decorative. It is the flag to honour if email is ever added; don't assume it does anything today.

### UI

shadcn/ui (`components.json`, style `base-nova`, base color `neutral`) with Tailwind CSS v4 — config lives in `app/globals.css` via `@theme inline` (no `tailwind.config.js`; the CSS is the config). Path alias `@/*` maps to the project root (see `tsconfig.json`). Component aliases: `@/components`, `@/components/ui`, `@/lib`, `@/hooks` (per `components.json`). ### v2 conventions (digital learning standard)

v2 (`docs/V2-UPGRADE.md`) brought the app in line with `docs/STANDAR-DIGITAL-LEARNING.md`. Keep these when changing UI:

- **Definition of done for UI changes:** `npx tsc --noEmit`, `npm run lint`, `npm run build`, then `npm run audit:a11y` against the running build (axe-core, WCAG 2.2 A/AA; exits 1 on any violation; currently 26/26 pages clean), plus a manual pass at 390px with the keyboard only. Automated checks find only part of the barriers. For any change to SQL/RLS or to a data reader, also `npm run test:rls` (`scripts/rls-check.mjs`: REST-level who-can-read-what as anon / non-enrolled learner / enrolled learner / owner and non-owner admin, plus the `?next=` redirect guard; exits 1 on any failed assertion; creates and deletes `c-rls-*@test.local` users).
- **Every control that calls the server shows that it is working.** `docs/STANDAR-UMPAN-BALIK-UI.md` is the operational rulebook (R1–R13) derived from `docs/STANDAR-DIGITAL-LEARNING.md` §5/§16/§17/§18; read it before adding any control that triggers a server action. The load-bearing points: `disabled={isPending}` **alone is not feedback** — the label must change too, and a spinner alone is not enough because `app/globals.css` freezes animations under `prefers-reduced-motion`. The shared primitives are `<Button pending pendingLabel>` (the standard way; `AlertDialogAction` is a `Button`, so it takes them too), `<SubmitButton pendingLabel>` for `<form action={serverAction}>` (wraps `useFormStatus`, which only reports the *parent* form and so must stay in a child component), `<StatusMessage>` for any error/success text (an always-mounted `aria-live` region — render it unconditionally, since a live region that appears together with its content often goes unannounced), `<SaveStatus>` for staged work, `<PendingRegion>` for lists being refetched, and `<Spinner>`. A server action whose failure the user must know about returns `{ ok: false, error }` rather than `void` — `toggleLessonComplete` (`app/learn/[courseId]/actions.ts`) was `void` and silently dropped lesson progress, which also silently withheld certificates. Pending indicators belong on the control that was clicked, not in a toast; toasts are the closing confirmation, and a clear navigation already *is* that confirmation, so don't add one on top. Indonesian pending labels use verb + `…` (U+2026, not three dots): Menyimpan…, Mengirim…, Memuat…, Mengunggah…, Mengimpor….
- **While one action writes, the controls that would conflict with it are locked** (same doc, §6, R14–R20). Locking a button protects that button only — the gap that matters is everything *else* still being live. Scope the lock to how far the damage reaches: one control (`<Button pending>`), one row (per-row id state), a whole form or dialog (`<BusyGuardProvider>` — every `<Button>` under it then refuses clicks while keeping keyboard focus; `ignoreBusyGuard` opts a control out), or a whole surface plus its exits (`<BusyRegion>`, which sets `inert`). `inert` removes its subtree from the accessibility tree, so never wrap the triggering button in it — that is what the guard is for. Route navigation is **not** a lock: it gets a skeleton (`app/**/loading.tsx` + `components/loading/*`, and note `loading.tsx` cascades to child segments, so a route with no file inherits its ancestor's shape). Prefer fixing the state bug over adding an overlay: the course editor's save used to overwrite `draft` with the snapshot it had sent (`CourseDraftContext`'s `commitSaved`), silently destroying anything typed during the save *and* clearing the localStorage backup with it — it now keeps newer edits and stays dirty, which removed the need to freeze the editor at all. Client-side locking is never the data guarantee: a second tab or a reconnect still gets through, so anything that must not happen twice is also constrained server-side.
- **Accessible names:** icon-only buttons and links need `aria-label` (or `sr-only` text) and `aria-hidden` icons; every `SelectTrigger` and `Switch` needs a label; `RichTextEditor` takes an `ariaLabel` prop. Status is never colour-only (write "Correct", "Done"); in-text links are underlined; targets are at least 24px.
- **App shells on phones:** `LearnerShell` and `AdminShell` use `hooks/use-mobile-nav.ts` — below `lg` the sidebar is an off-canvas drawer (`sidebarClasses()`; header "Buka menu" button, closes on navigation and Escape), from `lg` up it is the collapsible 250px column. Before this, the always-open 250px sidebar made every learner and admin page overflow at 390px. Keep new wide UI (tab lists, button rows, tables) wrapping or scrolling inside its own box.
- **Player layout:** `components/learn/LearnShell.tsx` owns the header / lesson / course-content layout for both `/learn/[courseId]` and `/admin-preview/[courseId]`; below `lg` the sidebar is a drawer. `LessonPane` renders `LessonFooter` ("Complete & continue" posts `toggleLessonComplete` with `continueTo`, which redirects to the next lesson).
- **Dashboard:** `getContinueLearning()` (`lib/enrollments-server.ts`) computes the next unfinished lesson and real progress per active enrollment; don't fake progress from anything but completed `lesson_progress` rows.
- **Quiz explanations** live in `public.question_explanations` (migration `20261028000000_question_explanations.sql`, `databaseSetup.sql` section 15), deliberately not a `questions` column: RLS is row-level and `questions` is readable by anyone who can read the course, so a column would leak the explanation (often the answer) before the quiz. A learner can read a row only after a submitted attempt for that quiz; `submitQuiz` returns them in `SubmitQuizResult.explanations`. Admin side: `AdminQuestion.explanation`, `DraftQuestion.explanation` (zod default `""` so v1 localStorage drafts still parse), diffed and upserted in `saveCourseDraft`.
- **Lesson notes ("Catatan saya")** live in `public.lesson_notes` (migration `20261029000000_lesson_notes.sql`, `databaseSetup.sql` section 16), one row per `(learner_id, lesson_id)`, max 20,000 chars (`NOTE_MAX_LENGTH` in `lib/notes.ts` mirrors the DB check). **Private to the learner by design:** every policy is own-row (`learner_id = auth.uid()`), insert/update also require an enrollment in the lesson's course, and there is deliberately **no admin/superadmin read policy** (personal study material, not assessment evidence; don't add one for a "learner insights" screen without a product/privacy decision). Code: `lib/notes.ts` (client-safe type/format helpers), `lib/notes-server.ts` (`getLessonNote`, `getCourseNotes`), `saveLessonNote` in `app/learn/[courseId]/notes-actions.ts` (zod-validated upsert; empty content deletes the row), `components/learn/LessonNotes.tsx` (autosave ~800 ms + on blur, serialized saves, `aria-live` status, "Coba lagi" on error without losing text, flush on unmount; rendered by `LessonPane` via its `note` prop for content lessons in learner mode only) and `components/learner/CourseNotes.tsx` on `/learner/courses/[id]` for enrolled learners.
- **The a11y gate opens the lesson card** (`scripts/a11y-audit.mjs`). While a lesson card is collapsed, the whole content panel — type picker, rich text editor, interactive upload — is not in the DOM, so axe reported the Lessons tab clean without ever seeing it. The interactive upload's file input had no accessible name and that `label` violation passed the gate repeatedly. The audit now expands the **last** Buka/tutup button (module toggles come first in the DOM; pressing the first one collapses the module and hides its lessons) and audits both `[pelajaran terbuka]` and `[materi interaktif]`. 91/91.
- **Operations (Supabase + Vercel):** use the `devops` subagent (`.claude/agents/devops.md`) for migrations, env vars, Auth config, deploys and logs; it reads `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `VERCEL_TOKEN` from the environment (never from chat), runs `bash scripts/ops-preflight.sh` first, and asks for explicit approval before anything that changes production. Setup and plain-language steps: `docs/OPS-AGENT.md`. Supabase SQL is run with `supabase db query --linked -f <file>` (Management API, no DB password); production may lack CLI migration history, so don't use `db push` there.
- **Lesson reordering** (`moveLesson` in `CourseDraftContext.tsx`) follows `arrayMove` semantics; a lesson dropped on a later lesson in the same module lands after it. The dnd-kit `KeyboardSensor` is the WCAG 2.5.7 alternative to dragging.
- **UI language is Indonesian–English bilingual, Indonesian first.** Every user-visible string lives in the single dictionary `lib/i18n/dictionaries.ts` (ID and EN side by side; TypeScript enforces parity, so a key added to one language fails to compile until the other has it). Server Components read it with `await getTranslations()` (`lib/i18n/server.ts`), Client Components with `useI18n()` (`components/i18n/LocaleProvider.tsx`) — calling the hook in a Server Component crashes the page at render while `tsc` and `next build` stay green, so check which kind of component you are in. **There is no `/[lang]` route segment**: the locale is a person's preference, stored in the `bahasa` cookie (immediate, works logged-out) and mirrored to `profiles.locale` (follows them across devices) by `setLocale()` in `app/i18n-actions.ts`; the reasoning is written out at the top of `lib/i18n/config.ts`. It can be changed from the header switcher (`LanguageSwitcher`) or from the Language card on both Settings screens (`components/i18n/LanguageSettingCard.tsx`) — both call the same action. Dates and numbers follow the active locale (`locale === "en" ? "en-US" : "id-ID"`), not a hardcoded `id-ID`. `<html lang>` follows it too.
  - **Measure it, don't assume it:** `npm run i18n:check` (`scripts/i18n-check.mjs`) opens the LMS in English and counts the interface lines still rendering in Indonesian, per screen — including dynamic routes whose ids it looks up in the database at run time. Screens listed in its `SUDAH_SELESAI` set fail CI if anything regresses; it currently reports **21/21 screens, 0 lines**. Course titles, lesson titles, question prompts, notification bodies and superadmin-authored landing copy are deliberately excluded as **content**, not interface. `npm run cek:bahasa` (`scripts/cek-bahasa.mjs`) separately enforces plain language (no interface sentence over 25 words; every abbreviation explained).
  - **Still Indonesian-only, on purpose:** the assembled validation messages in `lib/course-draft.ts` / `lib/course-draft-issues.ts` / `lib/lesson-completeness.ts`, which build sentences from fragments and only ever appear on a failed save. Code identifiers, DB enum values, routes, CSS classes and stored values stay English. Use the shared glossary in `docs/GLOSARIUM-UI.md` exactly (Kursus, Pelajaran, Peserta, Kuis, Studi kasus, Soal, Masuk/Keluar, Simpan, Terbitkan, "Selesai & lanjut", ...): formal "Anda", short sentences, no exclamation marks, no emojis. English error text from Supabase never reaches the page: auth errors go through `lib/auth/auth-error-message.ts`, database/storage errors through `lib/db-error-message.ts` (the raw message is only logged). DB-written text lives in SQL (`notify_on_enrollment()`'s title, the seeded `landing_content` row — see `supabase/migrations/20261028100000_indonesian_ui_text.sql`). Deliberate exceptions: grading CSV headers (`Attempt ID`, `Q N Score (<id>)`, ...) stay English because import parses them literally, and certificate descriptions still accept the legacy `[Student Name]`/`[Course Name]` tokens beside `[Nama Peserta]`/`[Nama Kursus]`. `scripts/a11y-audit.mjs` clicks editor tabs by their Indonesian names — update it if a tab label changes.
